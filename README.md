# mini-nest — власний IoC-контейнер і HTTP-диспетчер (частина 2/3)

Мінімальний DI-контейнер, який робить те саме, що `@nestjs/core` під капотом:
читає метадані типів параметрів конструктора й рекурсивно збирає граф залежностей.

## Структура

| Файл | Призначення |
|---|---|
| `src/decorators/injectable.ts` | `@Injectable()` — позначає клас як придатний до створення контейнером |
| `src/decorators/inject.ts` | `@Inject(token)` — параметр-декоратор для явного токена |
| `src/container.ts` | сам контейнер: `resolve`, `bind` |
| `test/tokens.ts` | символи-токени, якими тести реєструють залежності через `@Inject` |
| `test/` | тести (`node:test`) |

## Запуск

```bash
npm install
npm test
```

Компілює `src/` і `test/` через `tsc` (окремий `test/tsconfig.json`, бо декоратори — це не просто стирання типів, а повноцінна трансформація коду, яку вміє тільки сам TypeScript-компілятор) і запускає скомпільовані тести через вбудований `node --test` з увімкненим `--experimental-test-coverage` (поріг 100% на lines/branches/functions).

## Як це працює

`@Injectable()` — це декоратор класу, який викликається один раз під час завантаження модуля й кладе службові дані (scope) у метадані класу через `Reflect.defineMetadata`. Але головна магія відбувається без жодного рядка коду з вашого боку: коли на класі є **хоч один** декоратор і в `tsconfig.json` увімкнено `"emitDecoratorMetadata": true`, TypeScript-компілятор сам генерує додатковий виклик `Reflect.defineMetadata('design:paramtypes', [...типи параметрів...], Клас)` одразу після оголошення класу. Це не рантайм-фіча JavaScript — інтерфейси й типи стираються під час компіляції, тому `design:paramtypes` заповнюється лише для того, що лишається значенням у рантаймі (класи-конструктори), а все інше (інтерфейси, `unknown`, generics) перетворюється на `Object`.

Контейнер (`src/container.ts`) читає ці метадані через `Reflect.getMetadata('design:paramtypes', Target)`, отримує масив конструкторів-залежностей і рекурсивно резолвить кожен через `resolve()`. Якщо параметр має тип-інтерфейс (тобто в метаданих буде `Object`, а не конкретний клас), контейнер не знає, що саме туди підставити — для цього потрібен явний токен через `@Inject(token)`, який параметр-декоратор записує окремо в метадані класу (позиція параметра → токен), а контейнер перевіряє цю мапу токенів **до** типу з `design:paramtypes`.

Без `emitDecoratorMetadata: true` метадані `design:paramtypes` просто не з'являться на класі — і `Reflect.getMetadata` поверне `undefined`, тобто контейнер не зможе резолвити жодної залежності за типом взагалі.

Циклічні залежності (`A -> B -> A`) детектуються через масив шляху резолву (`path`), який передається рекурсивно: перед тим, як почати створювати клас, контейнер перевіряє, чи цей клас уже є в поточному шляху — якщо так, кидає помилку з повним ланцюгом (`[...path, current].join(' -> ')`) замість `RangeError: Maximum call stack size exceeded`.

## Як параметр-декоратор знає, куди підставити значення

Параметр-декоратори (`@Body()`, `@Param(name)`, `@Query(name)`) **не витягують дані самі** — вони лише записують у метадані класу інформацію про те, який аргумент звідки брати:

```ts
@Post()
async create(@Body() dto: CreateUserDto, @Param('id') id: string) { ... }
```

Коли декоратор виконується, він отримує три параметри: `(target, propertyKey, parameterIndex)`. На цьому етапі параметри просто індекси (0 для `dto`, 1 для `id`). Декоратор зберігає в метаданих методу карту вигляду:

```js
{
  0: { type: 'body', name: undefined },
  1: { type: 'param', name: 'id' }
}
```

Під час обробки HTTP-запиту диспетчер (клас `HandlerBuilder`) читає цю карту й будує масив аргументів:
1. Для індексу 0: читає тіло запиту й парсить JSON
2. Для індексу 1: витягує значення параметра `id` з URL через URLPattern
3. Викликає метод контролера з побудованим масивом: `method(...args)`

Валідація через `ValidationPipe` застосовується на кожен аргумент в порядку, перш ніж метод отримає його. Якщо DTO не валідна, виймається `BadRequestException` з HTTP 400 і деталями помилок.

## HTTP-маршрутизація

`@Controller(prefix)` позначає клас як контролер і реєструє базовий шлях:

```ts
@Controller('users')
class UserController { ... }
```

`@Get(path)` / `@Post(path)` — декоратори методів, що реєструють маршрут. Повний шлях будується як `/{controllerPrefix}{methodPath}`, наприклад:

```ts
@Get(':id')
getById(@Param('id') id: string) { ... }
```

`Factory.create(controllers)` приймає масив класів контролерів, резолвить їх через контейнер (з усіма залежностями), будує маршрутизацію й повертає HTTP-сервер, готовий до запуску через `server.listen()`.

## Частина 3: повний життєвий цикл запиту

Кожен HTTP-запит проходить один і той самий конвеєр, незалежно від контролера:

```
              ┌──────────────────────────────────────────────────────────┐
              │                     Factory.create()                     │
Request  ───▶ │  Middleware ──▶ Guard ──▶ Interceptor(before) ──▶ Pipe    │
              │                                                    │      │
              │                                                    ▼      │
              │                                                Handler    │
              │                                                    │      │
              │                                                    ▼      │
              │                                          Interceptor(after)│
              └──────────────────────────────────────────────────────────┘
                          │ throw на будь-якому етапі
                          ▼
                  Exception Filter ──▶ HTTP-відповідь (404 / 400 / 500 / ...)
```

- **Middleware** (`src/interface/middleware.interface.ts`, `src/decorators/use-middlewares.ts`) — єдина стадія цього циклу, яку постачає сам фреймворк, за аналогією з `NestMiddleware`/`app.use()` в реальному Nest. Це `use(context, next)` з явним `next()`, тому middleware може обгорнути **весь** інший конвеєр (наприклад, відкрити `AsyncLocalStorage.run()` навколо guard → interceptor → pipe → handler), а не просто виконатись і піти. `Factory.applyMiddlewares` (`src/core/factory.ts`) будує ланцюжок через `reduceRight`, той самий прийом, яким Express/Koa/Nest компонують middleware-стек.
- **Guard** повертає `boolean` до виклику pipe і handler — якщо `false`, кидається `ForbiddenException` (403), і обробник не викликається.
- **Interceptor** обгортає виклик: код до `next()` бачить вхід, код після — бачить (і може змінити) результат.
- **Pipe** трансформує/валідує кожен аргумент безпосередньо перед передачею в handler.
- **Exception Filter** — єдина точка, де помилка з будь-якого етапу (guard, interceptor, pipe, handler) перетворюється на HTTP-відповідь.

### Що з цього — фреймворк, а що — код застосунку

На відміну від частини 2 (де `ValidationPipe` — це вбудований у Nest примітив, а отже лежить у `src/pipe/`), у реальному NestJS `AuthGuard`, `LoggingInterceptor`, кастомний `ExceptionFilter` і ALS-обгортка над `requestId` **завжди пишуться самим розробником застосунку** — Nest не постачає їх "з коробки". Тому в цьому репозиторії:

| Шар | Розташування | Чому |
|---|---|---|
| `MiddlewareInterface`, `UseMiddlewares`, ланцюжок у `Factory` | `src/` | Це нова стадія самого життєвого циклу — фреймворк має знати, як її викликати, так само як він уже знає про guards/interceptors/pipes/filters |
| `ZodValidationPipe`, `AuthGuard`, `LoggingInterceptor`, `ExceptionFilter`, `RequestContext` (ALS-обгортка), `NotFoundError`/`ValidationError`, демо-сервіс | `test/fixtures/` | Конкретні реалізації під конкретний застосунок — так само, як у реальному Nest-проєкті вони лежать у `src/app/...` користувача, а не в `@nestjs/common` |

`test/lifecycle-order.test.ts` збирає мітки кожного етапу в масив і звіряє з точним порядком `['middleware', 'guard', 'interceptor:before', 'pipe', 'handler', 'interceptor:after']`.

### Чому AsyncLocalStorage, а не глобальна змінна

Якби `requestId` зберігався у звичайній змінній модуля (`let currentRequestId`), два конкурентних запити зламали б одне одного: перший запит записує свій id, віддає керування на `await` (наприклад, читання тіла запиту чи звернення до "бази"), і поки він чекає, event loop встигає почати обробку другого запиту, який перезаписує ту саму змінну своїм id. Коли перший запит прокидається після `await` і логує "свій" requestId — там уже чужий. Це не гіпотетичний випадок: `test/request-context.test.ts` явно шле 10 паралельних запитів з різними `X-Request-Id` і перевіряє, що жоден не переплутався з чужим.

`AsyncLocalStorage` вирішує це інакше: `als.run(store, callback)` прив'язує `store` не до модуля, а до **асинхронного контексту виконання** — Node відстежує цей контекст крізь усі `await`, `Promise.then`, таймери й колбеки, що були породжені всередині `callback`. Тобто кожен конкурентний запит живе у власній "бульбашці" контексту, і глибокий виклик (`UserService.getById` → `UserRepository.findById`, два рівні під обробником) читає саме `requestId` **свого** запиту через `storage.getStore()`, не отримуючи його як параметр і не ризикуючи побачити чужий. Ключова умова — `RequestContextMiddleware.use()` мусить обгорнути `als.run()` навколо **всього** іншого ланцюжка (guard → interceptor → pipe → handler), інакше код, що виконається поза цим `run()`, просто не побачить сховище.
